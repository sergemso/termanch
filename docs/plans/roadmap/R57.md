# R57 Keyboard navigation and discoverable actions for session tabs
Status: pending

Class: implement · Check: client unit tests and this ticket's desktop regression scenario pass in the existing Chromium e2e CI job.
Why: The session strip declares a tablist but has no arrow-key handler or roving tab stop; many sessions create a long Tab sequence.
Context: `packages/client/src/TabStrip.svelte` uses role=tab and aria-selected, prevents mouse focus, and exposes actions through long press and contextmenu.
Do: Use one tab stop in the strip, Left/Right and Home/End for focus, and Enter/Space for activation. Reveal the focused tab when overflowed. Make Windows and session actions accessible through explicit keyboard commands or labelled controls, including Shift+F10 for the context menu. Return focus to the originating tab or terminal as appropriate. Preserve frozen ordering during interaction and the detach/confirmed-close distinction.
Done-when: With 20 sessions on two servers, keyboard-only navigation reaches an offscreen tab, activates it, opens Windows and actions, cancels, and returns focus predictably; removing a focused tab chooses a valid focus target; no navigation key reaches the remote shell while focus is in the strip.

The scenario must expose the original failure and pass with the change; retain existing mobile/resource/bundle checks. R36 later runs these scenarios on additional engines and is not a completion dependency for this ticket.
