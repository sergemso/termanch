# Termanch Plan: native host mode (no Docker), signed releases and updater

Decisions: 0075 (native host mode, Docker host mode retired), 0076 (signed manifest, root-owned updater with rollback), 0077 (root actions by request file). Guardrails: `unprivileged-server-never-holds-root`, `updates-are-verified-and-reversible`, `host-mode-explicit-consent`, `host-changes-are-journaled`, `releases-are-signed`, `resource-constraints`, `no-paid-services`. Fact 0028 (baseline). Related plans: `termanch-v2-environment-and-ux.md` (B.2 host mode merged; S.3 signed releases; S.7 journal moved here as N.3; B.3 Add Server UI needs no change: the install words `host` and `host-user` stay) and `termanch-v4-ops-and-feedback.md` (D.3 host cleanup is replaced by N.6). A fresh session needs only this file, those artifacts and the repo.

Cold start: Rust workspace (`packages/core` wire types, `packages/server` the server, `packages/agent` parked). Server pieces: `src/main.rs` (args `TERMANCH_RUN=container|host`, `TERMANCH_RUN_USER`), `src/backend.rs` (`Runner` with `nsenter`, `RunMode`, tmux backend), `src/uninstall.rs`, `src/locale.rs`, `src/auth.rs`, `src/cert.rs`. Installer: `packages/client/public/install.sh` (Docker based, words `host-user`/`host`). CI: `.github/workflows/ci.yaml`, `docker-build.yaml` (native amd64/arm64 runners). The hosted client and installer deploy from master through Cloudflare Pages (`deploy-pages.yaml`). Today the server binary is glibc + OpenSSL dynamic, OpenSSL only through `reqwest` (workspace `Cargo.toml` line `reqwest = { version = "0.12", features = ["json"] }`); `str0m` uses `aws-lc-rs`. Tests: `cargo test --workspace`; browser e2e `packages/client/e2e/run.mjs` (see `docs/plans/termanch-v3-ui.md` cold start). The owner's own `termanch` container on the dev VPS must not be touched by tests; use a throwaway systemd test environment (a container with systemd, or `systemd-nspawn`) and free ports. Land each step as one squashed PR with green CI; merge only on the owner's "merge".

## Build and release

### N.1 Static musl binary without OpenSSL — [ ]‖
Class: implement · Needs: none · Check: `cargo tree -p termanch-server -i openssl-sys 2>&1 | grep -q 'did not match' && cargo build --release -p termanch-server`
Context: Fact 0028. `reqwest` is the only OpenSSL user. Targets `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`; CI already has native amd64 and arm64 runners (`docker-build.yaml`). `str0m` builds `aws-lc-rs` from source, which needs a C compiler and cmake.
Do: 1. In the workspace `Cargo.toml` set `reqwest` to `default-features = false, features = ["json", "rustls-tls"]` (webpki roots, so no system certificate store is needed); fix any compile errors. 2. Add a CI job `static-binary` building both musl targets on the native runners (install `musl-tools`, `cmake`; `RUSTFLAGS=-C target-feature=+crt-static`), failing if `ldd` shows a dynamic dependency, and uploading the binaries as artifacts. 3. Run the existing browser e2e against the musl binary on x86_64 (set `TERMANCH_BIN`) to prove WebRTC, tmux, PTY and the directory announce work; check RSS with the e2e gates. 4. Keep the Docker image build unchanged.
Done-when: `ldd` on both musl binaries reports "not a dynamic executable"; the e2e passes with the musl binary; `cargo tree -i openssl-sys` finds nothing.

### N.2 Signed release pipeline — [ ]
Class: implement · Needs: N.1 · Check: `cargo test -p termanch-server manifest`
Context: Decision 0076. No release workflow exists. The release key is an Ed25519 key kept as the GitHub Actions secret `RELEASE_SIGNING_KEY`; its public half, with a key id, is embedded in `packages/client/public/install.sh` and in the server binary (`packages/server/release-keys.txt`, same format as `cert-keys.txt`). `ed25519-dalek` is already a server dependency.
Do: 1. New workflow `.github/workflows/release.yaml` on tags `v*`: build both musl binaries (reuse N.1), write `SHA256SUMS` and `manifest.json` (`{version, kid, binaries: {x86_64: {url, sha256}, aarch64: {...}}, freeze: false, notes}`), sign the exact manifest bytes with the release key, attach `manifest.json`, `manifest.sig` and the binaries to a GitHub Release. 2. In the server crate add `release.rs` with `verify_manifest(bytes, sig, keys)` (key id lookup, Ed25519 verify) and a CLI `termanch-server --verify-release <manifest> <sig>` used by the installer and updater. 3. Unit tests: valid manifest, tampered manifest, unknown key id, wrong signature, freeze flag parsed. 4. Document in `SECURITY.md` how the key is created, stored, rotated and what a freeze does; do not print the key anywhere.
Done-when: the unit tests pass; a dry-run of the workflow on a test tag in a fork or with `workflow_dispatch` produces a manifest that `--verify-release` accepts and that fails after a one-byte change.

### N.3 Change journal, dry-run and revert (moved from v2 S.7) — [ ]‖
Class: implement · Needs: none · Check: `cargo test -p termanch-server journal`
Context: Decision 0067 and guardrail `host-changes-are-journaled`: everything the installer, profile or updater changes on a machine (packages, users, files, units, firewall rules) is journaled before it is applied; `termanch-server --revert` undoes journaled changes; the journal is root-owned so the unprivileged server user cannot alter it.
Do: 1. `journal.rs`: append-only JSON lines in a root-only directory (`/var/lib/termanch-root/journal.jsonl`), entry kinds `file_created`, `file_replaced` (with a backup path), `user_created`, `package_installed`, `unit_installed`, `firewall_rule_added`, each with enough data to revert and a timestamp. 2. `--dry-run` support: the installer prints the list of entries it would write before applying. 3. `termanch-server --revert [--only <kind>]` reverts in reverse order, skipping things that changed since (hash mismatch) and reporting them; user and package removal only when the entry says we created or installed them. 4. Tests in a temp directory for each kind, partial failure, and idempotence.
Done-when: installing then reverting in a temp root restores the starting state; reverting twice changes nothing; a modified file is reported, not deleted.

## Install and update on the host

### N.4 Native installer path — [ ]
Class: implement · Needs: N.2, N.3 · Check: `sh -n packages/client/public/install.sh && dash -n packages/client/public/install.sh && grep -q 'systemctl' packages/client/public/install.sh`
Context: `install.sh host-user|host` today installs Docker and starts a privileged container. It must now install natively: detect systemd (`/run/systemd/system`), else print a plain message pointing to the container install and exit; detect the architecture (`uname -m`: x86_64, aarch64); fetch `manifest.json` and `manifest.sig` from the latest GitHub release, verify with the embedded public key through the downloaded binary's `--verify-release` bootstrap or an embedded check, then the binary hash. Journal every change (N.3). Guardrail `host-mode-explicit-consent` and `releases-are-signed` apply.
Do: 1. New native branch for `host` and `host-user`: dry-run list, then create user `termanch` if chosen, install tmux with apt/dnf/yum/apk/pacman if missing, install the binary to `/usr/local/bin/termanch-server` (root-owned, 0755), create `/var/lib/termanch` for the run user, write `termanch.service` (`User=`, `KillMode=process`, restart on failure, environment for UDP port, client origin and claim secret handled as today) and start it. 2. Keep the UDP port selection and firewall steps from the Docker path (`ufw`, `firewalld`); keep the claim hand-over (`--claim`). 3. Container mode is unchanged. 4. Pin the embedded release public key in the script; the hosted copy is what Pages serves. 5. Tests: shellcheck-clean; a CI job that runs the installer inside a systemd-enabled container (for example `jrei/systemd-debian`) against a locally built release set and checks that the unit is active, the server answers `/health`, and `--revert` restores the starting state.
Done-when: the CI job passes on Debian and Ubuntu images, for root and `termanch` users; installing twice does not duplicate anything.

### N.5 Root helper and updater — [ ]
Class: implement · Needs: N.2, N.3 · Check: `cargo test -p termanch-server updater`
Context: Decisions 0076 and 0077; guardrails `updates-are-verified-and-reversible` and `unprivileged-server-never-holds-root`. The helper is a subcommand of the same binary (`termanch-server --root-helper <action>`), run by root-owned systemd units: `termanch-update.timer`/`.service` (daily) and `termanch-request.path`/`.service` (watches the request directory).
Do: 1. Updater: fetch the manifest, verify signature and hash, refuse when `freeze` is true or the version is not newer, keep the previous binary as `termanch-server.prev`, swap atomically (rename), restart the unit, poll `/health` for 30 s and roll back to `.prev` on failure; write journal entries. 2. Request handling: the directory `/var/lib/termanch/requests` (writable by the run user only for creating files), the path unit triggers the helper, which reads exactly one JSON file `{action, flags}`, accepts only `update-now` and `uninstall`, deletes the file, and never executes anything taken from it. 3. Unit files are written by the installer (N.4) and journaled. 4. Tests with a fake release server and a fake service manager: success, bad signature, frozen, health-check failure rolls back, malformed or unknown request ignored.
Done-when: the unit tests pass, including the rollback and the unknown-action cases; in the N.4 CI job an update to a newer test release succeeds and a deliberately broken release rolls back.

### N.6 Server requests and remote uninstall on the native host — [ ]
Class: implement · Needs: N.5 · Check: `cargo test -p termanch-server request`
Context: Decision 0072 (remote uninstall: owner connection, typed server name, certificate issued within the hour; stage 1 wipes the config, see `packages/server/src/uninstall.rs`) and 0077. This step replaces the nsenter route of plan v4 step D.3 for host mode; container mode keeps the copy-paste command.
Do: 1. Add `ClientMessage::UpdateNow` (owner only) and wire `Uninstall` flags (`delete_user`, `remove_tmux`, `kill_sessions`) so that on a native host the server writes the request file (0077) after the 0072 checks and replies `UninstallStarted`. 2. The root helper reverts the journal (N.3) honouring the flags (user and home only when ticked and created by us; tmux only when we installed it), stops and removes the unit, the binary and `/var/lib/termanch`. 3. Show the progress in the app per stage (client work stays in plan v4 step D.4). 4. Tests: each flag, refusal without a fresh certificate, helper removes only journaled things.
Done-when: in the N.4 CI job a remote uninstall leaves the machine as it started, and unticked flags leave the user and tmux in place.

### N.7 Migrate Docker host installs — [ ]
Class: implement · Needs: N.4 · Check: `sh -n packages/client/public/install.sh`
Context: Existing owners may have run the old host mode: container `termanch` started with `--pid=host --privileged`, `TERMANCH_RUN=host`, config in `/opt/termanch/home/.config/termanch`. Decision 0075 retires it.
Do: 1. In the installer, when `host` or `host-user` is requested and such a container exists, offer the migration: stop the container, copy its config directory (server key, owner, revoked devices) to `/var/lib/termanch` with the right ownership, install the native service (N.4) using the same UDP port, verify `/health`, then remove the container and image (journaled). 2. If anything fails, restart the old container. 3. Test in the N.4 CI environment with a fake old install.
Done-when: after migration the server id and owner are unchanged and the app reconnects without re-claiming; a forced failure leaves the old container running.
