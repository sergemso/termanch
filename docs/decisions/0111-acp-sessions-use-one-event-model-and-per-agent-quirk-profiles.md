## Decision

- **T0 is a new top tier of 0103, for sessions the server starts itself in ACP mode.** An ACP agent is a headless stdio child, so it cannot join or observe a TUI the user runs in tmux: those sessions stay T1 to T3 (hooks, screen profile, generic). The server owns the child (as it owns tmux sessions, 0054); client disconnects change nothing. Whether new sessions default to ACP when the agent supports it is the owner's call and is not made here.
- **No second event model.** ACP updates are mapped by a pure function in `adapters.rs` (as for hooks) into the existing `AgentEvent` stream (`packages/core/src/events.rs`) with `Source::Acp`, tier 0 like `Hook`, confidence high. Everything downstream (hub, attention, push, Home) is unchanged. The model gains only what T0 needs, all additive with `Unknown` fallbacks: `EventKind::Usage {used, size, cost?}` (context percentage is `used / size`), `EventKind::Title`, and a `Decision` payload on `Prompt` that carries the option ids and kinds, an optional diff or plan text, and how the answer is sent. `Tool` keeps name and one-line summary; raw tool input and output are never copied (0095).
- **What maps to what** (evidence: fact 0040): the open `session/prompt` is `Working`, its response is `Idle`/`Done` with the `stopReason`; `tool_call`/`tool_call_update` merge by `toolCallId` into `Tool`; `usage_update` into `Usage`; `session_info_update.title` into `Title`; `session/request_permission` and plan approval (`toolCall.kind: switch_mode`) into `Prompt`/`NeedsInput`; a question into `Prompt` only where the agent has a path (below). `plan` is accepted but not relied on (empty or absent for every agent measured); plan items come from kilo `todowrite` calls and from hooks.
- **Answers go back only as options the agent offered.** Show and accept `allow_once` and `reject_once` (0104), reply `{outcome: selected, optionId}` with exactly the tapped id; never offer `allow_always` or `reject_always` (this also avoids goose and claude "allow all" options). `session/cancel` interrupts and the server answers any open request `cancelled`.
- **Per-agent quirk profiles are data, not code**, in a server-side file next to the command allowlist (the client never supplies a command). A profile holds: the command and adapter package; the auth method; env it needs; which of `list`, `resume`, `close`, `fork`, `set_model` exist and whether `load` replays; the question path (`elicitation`, `permission_answers`, `ask_question`, `none`) and the client capabilities to advertise for it (opencode needs `elicitation.form`; fs and terminal are not advertised, so qwen and the rest run their own tools); the mode map from the product's words (ask, auto, plan) to the agent's mode ids; and known hazards with the response to each. Adding an agent is a profile plus fixtures (skill `probe-an-agent-over-acp`).
- **Hazards the profile must encode** (all measured, fact 0040): gemini wedges after a cancel with a permission open, so the server restarts that child and `session/load`s; the claude adapter refuses to start with `CLAUDECODE` set, so the child env drops it; a mode change can change the model (claude plan), so `configOptions` are re-read after `set_mode`; kilo's `question` tool hangs with no request, so its questions fall back to the screen path; an unanswered request blocks the turn forever, so the Home queue is the only way it ends, and it has a visible age.
- **Per feature, not per agent, degradation.** A missing capability drops that feature to T3 (screen tail, composer): a kilo session still gets the meter and plan items but a screen-based question. The tier label shows what is live.
- **Gates before any build:** adapter terms of use are read from primary text (fact 0040 has only secondary reports, and the Claude rules on subscription logins are the risk); memory per agent child is measured and the number of concurrent ACP sessions is capped to fit `resource-constraints`; U07a's tests use a scripted fake agent plus the recorded fixtures in `packages/server/testdata/acp/`.

## Why

Fact 0040 shows the agents agree on the core (a turn, tool calls, permission requests with `allow_once`/`reject_once`) and differ in bounded ways (questions, plans, usage, resume, hazards). The server already normalises hooks, scans and screens into one event stream; a second ACP-specific model would split Home, attention and push in two. A thin profile layer keeps the differences out of the code, matches the T2 profile approach of 0103, and lets a changed agent be re-measured and re-profiled without a release. Keeping T0 to sessions we spawn is the only honest scope: ACP cannot attach to a running TUI.
